## API audit notes

- The API currently exposes shared options support for the existing resources (`role`, `user`, `employee`, `department`, `designation`, `location`, `vendor`, `asset_category`, `module`, and `permission`). The resource schema currently models these same phase-one tables; assets, software, software licenses, credentials and requests are not implemented.
- The employee model defines `department_id`, `designation_id`, `manager_id`, `location_id`, and `user_id`, with Sequelize associations for department, designation, manager, location and user. The web employee form currently exposes only department, designation and location IDs.
- `users.role_id` and `permissions.role_id` / `module_id` are ID references. Role permission assignment has its own API flow. The user and employee list configs currently display some foreign key IDs instead of joined labels.
- Existing options endpoints are registered for the phase-one resource set, including users and employees. The API options reader has ID hydration and supports scalar allowlisted filters; the web list API's Sequelize array filters map to `IN` semantics.
- `ResourceModel.list` returns plain rows without association includes, so employee and user list responses do not currently provide the joined display objects required by the request. Employee update/add validation also does not verify active department, designation, location, manager, or user references. Bulk import does not resolve reference names/codes or provide a template.

## Implementation progress

- Web forms now use async ID selects for employee department, designation, location and manager, and user role. Optional references can be cleared. Edit values remain IDs and hydrate labels from each resource's `options` endpoint.
- Web list filters now include employee department, designation, location and manager, user role, master-record status, role status, and audit-log user. Reference filter chips show hydrated labels and submit ID arrays where multiple selection is enabled.
- Employee detail and employee/user tables resolve reference names through ID hydration when the API does not include the joined display object. Shared status and employment status constants drive form options and status badges.
- These rows remain `Planned` where the requested completion also depends on API-side active-record validation, joined response objects, import resolution/templates, or dependent-field constraints. The API directory is outside this session's writable root, so no API source was changed in this pass.

## Questions

- What exact values should be allowed for role `type`, request type/status/priority, license type, credential type, provided-by, and approval status? The current repository does not provide a complete authoritative set for the planned modules.
- Should designation be constrained to a department? The current schema has no `department_id` on designation, so that dependency cannot be inferred from the current data model.
- Which roles, if any, should be eligible as managers, approvers, or reviewers? No role policy for these references appears in the current source.
